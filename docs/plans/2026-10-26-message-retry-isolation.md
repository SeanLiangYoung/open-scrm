# 消息失败重试的企业隔离

根执行者审查当前代码发现：`MessageController.retryMessage`没有传企业身份，`retryFailedMessages`仅按日志ID和失败状态查询。因此可以重试别的企业失败日志，违反夜间计划的企业隔离要求。当前只发现一个生产调用点，修复须保持按本企业日志重试的既有响应结构。

## 任务与验收

1. 先补失败回归：企业A传入企业B日志ID，不调用发送、不修改B日志；A/B混合ID仅处理A；本企业失败日志仍可重试。断言实际查询含corpId，不能仅靠测试仓库自动过滤掩盖缺陷。
2. 控制器从可信上下文取得企业身份并传服务；服务入口验证正安全整数企业和非空、有界、去重的正安全整数日志ID。拒绝缺失/不合法身份和ID时无查询/写入。明确限制单次最多100条，防止无界批量。
3. 同企业已成功/不存在的ID仍不重发；外企ID不可泄露内容。至少覆盖6个行为类别，记录具体红绿用例数。
4. 消息服务单测、类型检查通过。若共享真实HTTP组已释放，再增加独立双企业实际HTTP检查，全部使用Mock5和全新隔离库，不连接真实提供方。

## 分工与限制

consent任务独占message控制器、发送服务、相关DTO及新增重试测试；主执行者维护计划/事实总证据。渠道真实性问题另行审查，避免同时改变发送语义遮蔽隔离修复。不能把当前修复称为跨服务exactly-once或完整营销合规改造。

执行者完成服务17例红→绿、控制器及实际DTO13例通过，消息完整13文件128项及类型检查通过。实际auth/message/gateway构建和专用PG16/Redis双企业网关八组验证通过（open-scrm-message-retry-http-TGYAsp），cleanup通过。新脚本已纳入统一HTTP组。根执行者仍须独立复验；后续渠道能力会保持此企业过滤并重跑，不能把渠道拒绝代替此隔离证明。
