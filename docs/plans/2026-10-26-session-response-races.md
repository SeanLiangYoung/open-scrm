# 会话切换后的迟到响应隔离

用户授权夜间持续推进。身份边界交叉审查已用实际Axios/Pinia/Vue复现：旧企业A的请求发出后，用户退出并登录企业B，随后A请求的401清除B的新token并跳转登录页。登录store已有序号保护，但API拦截器未检查失败请求所属会话。

## 实施与量化验收

1. 对admin和operation两端分别增加实际当前源码回归，先观察迟到401错误清空新凭据，再实现会话匹配判断。请求发出时捕获身份；仅当前会话自己的认证失败可以清理当前凭据。
2. 两端各覆盖：当前会话401仍退出；退出再登录后旧401不影响新会话；切换企业后旧401不影响新会话；登录401仍保留输入与已有特定错误反馈；没有可归属凭据的旧请求不误清新会话。保留现有登录先后次序10项检查。
3. 运行实际Axios/Pinia/Vue探针及两前端类型检查；完整HTTP回归当前串行进行，修复不与服务clean构建重叠。再同步事实文档、整体门禁及需要的浏览器验证。

## 文件归属与边界

customer任务独占两端utils/api.ts和会话竞态探针；主执行者维护计划/总证据；其余任务不得覆盖。此批不自动刷新凭据，不调整服务端授权，不触碰现有数据库，不发送外部消息。

完成标准是红绿证据与原有行为同时成立，不能仅以拦截器代码外观判断。08:00收口时未完成则明确保留。

实现完成，两端请求携带本地会话代次与发出时token；最新成功登录推进代次，迟到旧登录成功不会推进。相同JWT退出重登亦可区别。实际Axios/Pinia/Vue探针先6失败/8通过，补旧登录成功场景再2失败/14通过，最终16/16通过；原store竞态10/10通过。主执行者独立运行新探针16/16通过，并增加Chromium回归：真实Vite页面登录企业A、持有A请求、调用当前store退出并登录B、释放A的401，确认B凭据和路由保留。两端完整登录套件分别11/11通过，0跳过，日志 `/tmp/open-scrm-tenant-browser-admin-final.log` 与 `/tmp/open-scrm-tenant-browser-operation-final.log`。接口为模拟，未宣称真实后端会话验证。两前端类型检查与API文件lint通过；新探针已加入统一static组，当前注册23阶段，全组后续复验。
